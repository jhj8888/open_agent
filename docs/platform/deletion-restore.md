# 恢复旧备份时保留任务删除

V1.69 增加恢复请求拒绝记录与删除清单合并。调用链为受信源库 → 官方 MySQL CLI 导出普通删除记录及历史恢复 fence → 隔离副本迁移到当前 API → 停止副本 API → 同一 MySQL 事务合并 → 重新启动副本验收。没有新的公开导入接口，不改变模型、Skill 或沙盒的访问权限。

对于快照中已存在的任务，合并核对租户、环境、部署、提交者、请求及执行摘要、终态和资源释放状态，随后补回墓碑/恢复审计、撤销文件发布并重新安排精确键清理。清理键缺失或任一冲突拒绝整批。源库已清理不代表恢复出的对象已清理，因此重新打开待清理状态。其他保留任务文件不变。

对于快照之后才创建又删除的任务，恢复数据库没有该任务/部署/租户也能在 `oa_run_deletion_fence` 保存最小身份信息。该表没有外键，不能授予任何权限，只让 RunLedger 在既有授权之后拒绝原请求键：原提交者得到 409 `run_deleted`，其他提交者不可访问。不会伪造任务正文、用量或历史执行记录；新请求键仍执行正常的权限、配额与准入检查。

合并可重试，不重复恢复审计；缺少旧账本的 fence 仍可再次导出。合并事务使用官方 MySQL 客户端，禁用自动重连、不使用 `--force`，失败退出会回滚连接内未提交事务。输入先校验，动态文本用 UTF-8 十六进制字面量，不拼接原始 UID/请求键到 SQL。每次最多 50,000 条，超限失败不截断。

## 运维边界

恢复工具要求当前已部署 API 含 V1.69，并核对源 JAR 与运行容器挂载及发布摘要。旧快照原始数据库指纹先核验，随后才执行新迁移与删除合并；“指纹一致”不能描述合并后的数据库。目标仅限本项目恢复副本，独立内部网络、无宿主端口、执行准入关闭且合并时 API 停止。没有启动 worker 或向模型重放任务。

隔离演练从仍在线的源库取删除截点，不代表生产切换完成。实际切换须停止旧入口和写入者，再取得最后的受信删除清单、合并并验收后开放新入口。丢失且没有备份/PITR 的删除不能被推断，当前不承诺零 RPO。源清单包含 UID/请求键，只保存在 root 私有恢复目录；不得发送到公共日志或 Git。完整操作及既有 Restic 备份范围见[备份手册](../../deploy/platform/backup/README.md)。

已有删除或恢复 fence 时，不得回退到忽略相应记录的旧 API。保留 V1.68/V1.69 数据与审计；需要回退时应使用同样检查删除记录的代码，或先关闭入口再进行受控恢复。浏览器删除交互和生产集群切换/灾备验收仍独立跟踪。
