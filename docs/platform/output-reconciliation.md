# 任务产物对账与迟到上传恢复

V1.67 修复一个真实 MySQL/S3 演练发现的漏清理问题：上传被阻塞期间，对账已将其记录置为 `cleared`；旧上传随后恢复，将对象写入 S3，并在发布前被强杀。旧对账永久跳过 `cleared`，因此该对象会残留，但不会出现在用户的可下载文件列表。

修复后的 `cleared` 表示“最近一次精确键清理成功”。系统保留未发布对象的清理记录，并定期复查，处理第一次删除后才完成的旧写入。任何已被发布文件引用的对象键都跳过删除。失败文件重试继续生成新的不可变键，不覆盖原文件。

| 状态/操作 | 调度规则 |
| --- | --- |
| 首次失败候选清理 | 上传记录创建超过 15 分钟且已到处理时间 |
| 存储离线或清理失败 | 保持 `reaping`，至少 5 分钟后重试 |
| 成功清理 | 标记 `cleared`，24 小时后再次复查精确键 |
| 旧上传在清理后报错 | 若键未被引用，将 `writing/reaping/cleared` 重新标记 `abandoned`，安排对账 |
| 每轮扫描 | 按到期时间排序，最多 20 条；已发布对象不参与清理 |

实际调用链为 `RunLedger.submit/claim → TaskOutputService.reserve/upload → MinioTaskOutputStore → 官方 Minio SDK → SeaweedFS`；恢复使用同一 `TaskOutputService.reconcile` 与 Spring JDBC 事务。S3 bucket policy、Skill 输入文件前缀、Redis/Kafka、模型执行和用户授权流程均不变。

## 实测内容

27 项 Java 检查通过，包含 6 项真实 MySQL 产物用例，以及内部接口权限和 Spring 启动检查。新增数据库回归覆盖迟到对象再次清理、清理失败退避且不阻塞其他候选、并发清理后的上传异常重新登记；这些用例已被现有 CI 的 `Run*Test` 选择器覆盖，远端 CI 结果另行核对。

独立非 root MySQL/SeaweedFS 容器和多个 Java 进程完成九阶段演练：

1. 通过真实任务账本和上传服务发布一个保留文件。
2. 在另一个对象已写入 S3、数据库仍为 `writing/pending` 时强杀上传 JVM。
3. 强杀 S3；实际对账保持待重试状态，新上传失败且没有公开对象引用。
4. 重启 S3；对账清理遗留对象，错误摘要重试使用新键发布，保留文件仍完整。
5. 另一个上传在第一次读取前暂停；将其测试记录时间前移，实际对账先完成清理。
6. 解除暂停，独立进程验证对象已经迟到写入，但数据库仍无发布引用；再次强杀上传 JVM。
7. 将测试调度时间推进至复查到期，实际对账清除迟到对象，最终 4 个上传记录已清理、2 个已发布文件内容及摘要正确。

旧制品 `75927e…f9c45` 在 `late-recover` 阶段失败；修复制品 `300817…56722b` 在相同关键场景通过。完整摘要、阶段和部署复查见 [验证记录](output-reconciliation-verification-20261106.json)。测试容器、卷和凭据均已清理，没有改写展示业务数据。

演练使用已核对摘要的 API JAR 内实际业务类、迁移及依赖，运行 V1.49–V1.67 和必要上游表；模型、租户身份为合成测试数据，没有调用模型或走公开 HTTP 鉴权。为了可重复执行，直接推进测试库中 `created_at/reconcile_after` 时间戳，没有实际等待 15 分钟或 24 小时。真实 multipart 中途断流/未完成分片治理、任务删除、完整权限矩阵和生产容量仍需验收，不能据此关闭整个产物交付变更。

## 运维与复现

展示 API 已更新至 V1.67，维护前保存私有 SQL 备份，维护耗时 41.65 秒。更新后原任务 58 步、2 个文件下载摘要、缓存/新增 Token、四个统计周期及 21 项公网列表/详情用量一致性复查通过；没有重放模型或工具任务。集群执行准入仍保持原状态。

V1.67 为 `oa_run_output_upload` 增加 `reconcile_after` 和调度索引，不删除旧行或对象。就绪检查要求新字段存在。清理记录随任务数据一起备份，在显式任务删除流程完成前不自动丢弃。回退旧代码会恢复旧的漏清理行为；新增列与索引应保留，数据库恢复按既有备份手册执行。

每日复查会产生持续的数据库和 S3 请求；待清理积压或存储长时间不可用时，实际回收延后，需纳入容量与告警验收。日志仅记录上传 ID 和固定失败说明，不记录凭据、正文或原始存储错误。

使用 `package_output_store_probe.py --probe OutputReconciliationProbe`，以 Java 21 和固定 API JAR 编译为 `output-reconciliation-probe.jar`；其余参数同[存储层演练](output-store-recovery.md)。将 probe 放到 `verify_output_reconciliation.py` 同目录，在已授权展示机运行。脚本检查可用内存至少 1.5 GiB，仅使用已缓存的固定镜像，不开放宿主端口，所有进程共用临时 MySQL 的无外网网络命名空间。仅在自建资源上强杀进程和清理卷。
