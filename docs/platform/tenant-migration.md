# 租户与环境迁移

变更：`manage-tenant-access`。本页记录 V1.49 的边界和操作步骤；全部资源入口的接入、管理界面和内部服务身份仍由该变更的后续任务跟踪。

## 调用链与影响

Casdoor JWT → Spring Security → `JwtClaimsFilter` 的已验证 UID → 资源服务调用 `TenantAccessService.require` → `TenantAccessRepository` 查询成员、账号状态与空间存续状态 → 环境角色矩阵 → 资源服务使用返回的 tenant/environment 查询数据。

本次新增 `commons.tenant` 和五张 `oa_` 表，沿用 Spring JDBC 与现有 MySQL。没有改写既有空间、用户、认证过滤器、Redis、Kafka 或对象存储配置。新表授权入口不缓存角色；删除旧空间成员或冻结账号会立即阻止后续授权。仅加入这个入口并不代表旧资源 API 已全部收敛，后续必须逐个接入与验证。

## 映射与角色

- 未删除空间映射为 `space-<space_id>`，不根据客户端头部重建归属。
- 未删除用户的个人资源映射为 `user-<SHA256(uid)>`，UID 按大小写精确匹配。
- 旧空间 owner/admin 映射为测试环境租户管理员，member 映射为测试开发者；个人租户本人为测试管理员。
- 每个租户创建 test/prod 两条环境配置，**不迁移任何生产成员授权**。平台管理员表初始为空，需由部署引导程序显式登记已验证身份。
- 新账号/空间的生命周期接入在后续治理任务完成前，不应宣称新增租户管理已经可用。

| 角色 | 测试环境 | 生产环境（须另行授予） |
|---|---|---|
| 租户管理员 | 元数据、编辑、运行/取消、日志、成员/配额/凭据、审计 | 元数据、取消、日志、成员/配额/凭据、审计 |
| 开发者 | 元数据、编辑、运行/取消、日志 | 仅元数据 |
| 运维 | 元数据、运行/取消、日志 | 元数据、取消、日志、发布/回滚 |
| 只读 | 元数据 | 元数据 |

生产执行需要单独的部署授权，不能从上述角色推导。平台管理员负责治理，不隐含租户运行数据权限。停用租户后拒绝新任务、资源修改与凭据变更，获授权管理员/运维仍能查看历史和取消存量任务；归档后仅保留历史读取。

## 发布前与核对

1. 备份数据库及 Flyway 历史，记录旧空间、用户、成员数量；先在副本执行迁移与测试。
2. 按正常 Flyway 顺序应用 V1.49。它仅新增表并回填，不修改上游历史脚本。
3. 核对 `oa_tenant` 中 space 数与未删除空间数一致，personal 数与有效非空 UID 数一致；复核未知旧角色、孤立成员、已冻结用户。冻结用户可能保留历史映射，但授权查询必须拒绝访问。
4. 核对 `oa_tenant_member WHERE environment='prod'` 行数为 0；平台管理员行数为 0。管理员再按生产授权流程登记。
5. 配额初始值为每环境运行并发 4、队列 32、沙盒 4、每日 token 1000000、审计 180 天。此处定义配额；原子准入与计量由 `persist-agent-runs` 实现，不能把配置值当作已生效限流。

新资源、缓存与对象键必须使用 tenant/environment 复合边界。暂不自动将所有旧资源归入生产；旧资源迁移将在各资源变更中明确执行。

## 回滚

V1.49 为新增表迁移，可停用新入口并保留这些表和审计，回退至仍执行租户授权的兼容版本。**禁止为了回滚删除审计、自动执行 Flyway repair，或恢复未经环境授权的旧访问路径。** 如果迁移在 MySQL 非事务 DDL 期间失败，先隔离流量、保留数据库副本，再按实际完成语句核查修复，不能盲目重跑或清空业务表。

本仓库首次导入时曾清理 V1.16 的样例密钥；接管已有上游数据库时必须单独核对 Flyway checksum，不能直接套用空库初始化流程。
